Skill-Gap Analyzer & Career Path Recommender

Build it in dependency order, not in stack order

Nine stages, each one gated. The rule underneath all of them: the thing most likely to kill this project is bad skill extraction, so that gets proven before a single route or component exists.

ASSUMES ~4 WEEKS OF PART-TIME WORK. If your deadline is tighter, cut Stage 6 to a single unstyled page and cut to 2 roles — never cut Stage 3. If it's longer, spend the extra time in Stages 2–4, not on the frontend.

Decisions locked before Day 1

These were open in your plan. Leaving them open costs you days later, so close them now.

Backend FastAPI You're serving an ML pipeline. Django's ORM and admin buy nothing here and cost deploy weight.
Database Postgres via Supabase The data is deeply relational — postings, skills, aliases, join tables. And pgvector is there if you want it.
Frontend React + Vite One page, no router, no state library. Vite because the build is instant and Vercel deploys it with zero config.
Skill source Curated taxonomy first ESCO or Lightcast Open Skills as the backbone. Embeddings only resolve variants the dictionary misses.
Job data Frozen snapshot, committed No live scraper in the request path. A demo that depends on a scraper is a demo that breaks in an interview.
Roles Three, maybe four 300 good postings for one role beats 40 each across fifteen. Thin per-role data is what kills these projects.

The stages

Each stage ends with a gate. The gate is a thing you check, not a feeling — if it fails, you stay in that stage.

00Today · 2h

Foundation

Heads up: I checked your machine — Git is installed, but Python and Node are not. That's the first thing to fix, before anything else here.

  • Install Python 3.11 (not 3.13 — some ML wheels still lag) and Node LTS. Tick "Add to PATH" in the Python installer.
  • Create the repo and the folder structure below. Push it.
  • Write the README now, not at the end: the problem in three sentences, the dataset you're using, the architecture, and an empty "Results" heading you'll fill in at Stage 3.
  • Set up a virtualenv and pin dependencies in requirements.txt from the start.
# after installing Python 3.11 and Node
python -m venv .venv
.venv\Scripts\activate
pip install fastapi uvicorn spacy sentence-transformers psycopg[binary] pandas
Gate

python --version and node --version both answer, and GitHub shows a repo with a README that explains the project to a stranger.

01Days 1–3

Data foundation

  • Pick the job-postings dataset and freeze it. Load raw rows into Postgres, then clean in SQL so the cleaning is reproducible and reviewable.
  • Dedupe hard. Job boards are full of the same posting reposted. Duplicates will silently inflate every frequency number you compute later.
  • Build the skills table from the taxonomy: canonical name, aliases, category. This is the backbone of everything downstream, so it's worth a full day.
  • Split each posting's text into required vs preferred sections where the wording allows. This distinction is what will make your output feel smart later.
Gate

At least 250 deduped postings per target role. If a role can't clear that bar, cut the role — don't ship a role backed by 40 postings.

02Days 4–7

Extraction pipeline, offline

No web server yet. This is a script that reads a text file and prints a list.

  • Taxonomy matching with alias normalization — Node, NodeJS, Node.js all collapse to one entity. This does most of the work.
  • Use spaCy for what it's actually good at: tokenizing, sentence splitting, and noun-phrase candidates — not for named-entity recognition of skills. Off-the-shelf NER won't tag Kafka or gRPC.
  • Add embedding similarity (all-MiniLM-L6-v2) as a fallback for candidates the dictionary misses. Log every fuzzy match so you can inspect the bad ones.
  • Handle the resume side: crude section detection so "Skills" and "Experience" are weighted differently from "Interests".
  • Pasted text is the primary input. PDF parsing is a swamp of two-column layouts and tables — it's a Stage 9 stretch, not a Week 1 problem.
python -m analyzer.extract --file resumes/me.txt
# → python, fastapi, postgresql, docker, git, rest-api ...
Gate

Run it on your own resume. The output is recognizably you — no phantom skills, and nothing obvious missing.

03Days 8–9

Evaluation — the go / no-go

This is the stage nobody else's project has. A student project with a real metric in the README stands out immediately, and it gives you ten minutes of interview material. Do not skip it because it feels like a detour.

  • Hand-label 40 postings with the skills they actually require. Boring, roughly three hours, worth every minute.
  • Compute precision and recall against your extractor. Write the numbers into the README's Results section.
  • Read the false positives and false negatives one by one. They will tell you exactly what to fix — usually alias gaps and section-boundary bugs.
  • Iterate on Stage 2 until the numbers move. Keep the labeled set in the repo as a regression test.
Gate — hard stop

Recall ≥ 0.70 on hard technical skills. Below that, go back to Stage 2. Every downstream number — the gap score, the ranking, the roadmap — inherits these errors, so shipping a pretty frontend on top of bad extraction just hides the problem.

04Days 10–14

Gap logic and roadmap

This stage is the whole project. Stages 5 through 8 are packaging. Budget accordingly.

  • Precompute role profiles offline: for each role, each skill's frequency across postings, split by required vs preferred. Store the result. The API must never scan 10,000 postings at request time.
  • Gap score = weighted coverage of the role profile. Keep it as the headline number, but make the evidence the product.
  • Rank by marginal coverage, not raw frequency: which single skill, learned next, unlocks the most postings you currently fail? That's greedy set cover — about ten lines — and it's a far better answer than "sorted by frequency."
  • Prerequisite graph: hand-encode dependencies for ~100 skills so the roadmap is topologically sane. No recommending Kubernetes before Docker.
  • Resource map: a curated JSON of skill → free resources. Be honest that it's curated, not learned. A good hand-built map beats a bad recommender, and interviewers respect the distinction.
python -m analyzer.gap --resume resumes/me.txt --role sde1-backend
#  Coverage: 61%  (of 340 SDE-1 Backend postings)
#  1. Kafka   — in 68% of postings, blocks 231  → [resource]
#  2. Docker  — in 54% of postings, blocks 118  → [resource]
Gate

Run it on yourself. The top three recommendations are things you'd genuinely go learn this month. If they aren't, your ranking is wrong — fix it here, where it's still a fifty-line file.

05Days 15–17

API

A thin wrapper. If this takes more than three days, logic is leaking out of Stage 4 and into your routes.

  • Three endpoints: GET /roles, POST /analyze, GET /resources/{skill}. That's it.
  • Role profiles are read from the precomputed table. Only the resume is processed live.
  • Pydantic response models from day one — they become your frontend's contract and your API docs for free.
  • Plan for the free-tier memory wall now: Render's free instance is 512MB and cold-starts after inactivity. Loading spaCy and a transformer together can blow it, and a 60-second blank screen in front of a recruiter is the failure mode to avoid.
  • If dictionary matching alone gets you through the resume path, skip loading the transformer at runtime entirely.
Gate — measure it, don't assume

Cold start under 10 seconds and resident memory under 400MB. Check with /analyze on a real resume, not on an empty request.

06Days 18–21

Frontend

  • One page. A textarea for the resume, a role dropdown, an Analyze button, and a results view.
  • Results view: the coverage number up top, then the ranked gaps as cards — each showing the skill, the evidence sentence, and the resource link.
  • Show a real loading state. Your first request will hit a cold backend and take several seconds; a frozen button reads as broken.
  • Show the skills you did find in the resume too. It builds trust in the output and makes extraction errors visible instead of hidden.
Gate

A friend who has never seen it can paste a resume and understand the result without you narrating. Watch them do it and don't help.

07Days 22–24

Deploy

  • Supabase first (the DB others depend on), then Render for the API, then Vercel for the frontend.
  • Budget a full day for the boring failures: CORS, environment variables, the Postgres connection string format, and the build that works locally but not in CI.
  • Seed the deployed database from your committed snapshot with a script — never by hand, or you can't redo it.
Gate

It works from your phone, on mobile data, with the laptop closed. That catches the localhost URL you left hardcoded somewhere.

08Days 25–28

The story

Skipping this stage is why good student projects get ignored. Treat it as engineering work, not paperwork.

  • README: problem, live link, demo GIF above the fold, architecture diagram, the Stage 3 metrics, how to run it locally.
  • A demo GIF beats a screenshot and massively beats a wall of text. Fifteen seconds, no audio.
  • Write the honest self-analysis section: what the tool said about your own resume, what it got right, what it got wrong, and why. This is the most memorable thing in the whole repo and nobody else does it.
  • A "Limitations" section. Naming your own weaknesses first is the single strongest signal of engineering maturity you can put in a README.
Gate

A stranger reading the README for 60 seconds can say what it does and how well it works. Test this on someone non-technical.

Repo structure

Set this up in Stage 0. The analyzer/ package is importable and testable with no server running — that's what makes Stages 2–4 possible.

How we work each session

Since I'm running inside the repo, the loop is tighter than paste-and-fix.

  1. You open with the stage and the goal — "Stage 2, alias normalization" — so I'm not guessing at context.
  2. I write the code across the files it touches and run whatever can be run without your credentials.
  3. You run the thing that needs real data or a real key, and paste back the output or the traceback.
  4. We iterate until the stage's gate passes. Then you commit with a message that says what the stage did.
  5. Commit at every gate at minimum. Recruiters open the commit list, and four commits named "final" reads badly.

Deferred — only after Stage 8 ships

Each of these is a real feature. Each is also a way to spend three weeks and never deploy. The order here is by payoff.

PDF resume upload — with an editable "check what we extracted" step, because the parse will be wrong sometimes and silently wrong parsing is worse than no parsing.

An LLM extraction baseline — run the same 40 labeled postings through a model and compare against your taxonomy approach. Whichever wins, you have a genuinely interesting result and a great interview answer.

More roles — by then it's a data task, not a code task, which is exactly the right thing to be able to say.

Auth and progress tracking — deliberately last. It needs users and elapsed time to show anything, so at demo day it's an empty chart. The prerequisite graph in Stage 4 is the better use of the same effort.
